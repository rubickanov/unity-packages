# Audit findings — com.rubickanov.devconsole.netcode

Generated by automated review.

## Critical (correctness / bugs)

- **[FIXED]** Cheat protection is enforced only on the client; the server RPC bypasses it — `Runtime/NetworkCommandBridge.cs:112-119` — `ExecuteOnServerRpc` sets `CommandRegistry.Instance.PreExecuteFilter = null` and then calls `CommandRegistry.Instance.Execute(rawInput)`. With the filter removed, the server executes whatever command name the client sent with **no** `_cheatProtected` / `CheatsEnabled` check and **no** domain check. The only place cheat protection is evaluated is `FilterCommand` (line 77), which runs client-side before the RPC is sent. A modified client can invoke `ExecuteOnServerRpc` with a cheat-protected, Server-domain command name even when `sv_cheats` is `0`, and the server will run it. This contradicts the component's own doc comment ("Server-authoritative flag controlling whether cheat-protected commands are allowed", line 18) and the package's stated purpose. Note that the blanket filter-removal is not even needed to "avoid recursion" for the cheat check: a Server-domain command re-entering `FilterCommand` on the server returns `null` (line 92, `NetworkManager.IsServer`) and a cheat-protected one returns an error before executing — so the cheat/domain check should be re-applied server-side (e.g. re-check `_cheatProtected`/`CheatsEnabled` and `_domains` inside the RPC, or keep the filter and only guard against re-routing) instead of disabling all enforcement.

## Minor (conventions / shortcomings)

- **README command examples will not register as commands** — `README.md:25-31, 45-49` — the examples show methods annotated only with `[CommandDomain(...)]` (e.g. `[CommandDomain(CommandDomain.Server)] public static string Kick(string[] args)`). Command discovery in the base package registers methods only when they carry `[ConsoleCommand]` (`CommandRegistry.DiscoverCommands`), and `ScanCommandAttributes` (line 41-55) only assigns domains to commands that are already registered. A method with `[CommandDomain]` but no `[ConsoleCommand]` is never registered, so the domain/cheat attribute has no effect. The signatures also don't match the real API (the actual commands in `Runtime/Commands/NetworkCommands.cs` use typed parameters like `Kick(ulong clientId)`, not `string[] args`). The examples should include `[ConsoleCommand(...)]` and realistic typed signatures so a copy-paste actually works.

- [x] **`sv_cheats` built-in command is registered on every spawn but never unregistered** — `Runtime/NetworkCommandBridge.cs:57-72, 36-39` — *(Fixed: `OnNetworkDespawn` now unregisters `sv_cheats`, mirroring the spawn-time registration.)* — `RegisterBuiltInCommands` registers `sv_cheats` in `OnNetworkSpawn`, but `OnNetworkDespawn` only clears `PreExecuteFilter` and leaves the command registered. After despawn the filter is gone, so a client typing `sv_cheats 1` falls through to the handler locally, hits `!NetworkManager.IsServer` (line 64) and silently returns `null` (no feedback). Unregistering `sv_cheats` in `OnNetworkDespawn` would keep the registry consistent with the local-only mode the despawn is meant to restore.
